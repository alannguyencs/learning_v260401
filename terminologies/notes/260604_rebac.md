## ReBAC (Relationship-Based Access Control)

**In one sentence:** ReBAC is an authorization model that decides "can this user touch this resource?" by asking **whether a relationship path connects them** in a graph (e.g. *you manage the person who owns this record*), rather than by checking a static role — which is exactly how the `/librarian` natural-language-to-SQL agent guards every database read.

### Key terminologies
These build on each other; read top to bottom and the last term (ReBAC) falls out naturally.

```
                        Authorization
                  (what may this user do?)
                            │
            ┌───────────────┼───────────────┐
            ▼               ▼                ▼
          RBAC            ABAC          "we need paths,
      (user's role     (user vs.        not just role
        only)         the resource)     or flat details"
            │               │                │
            └───────────────┴────────────────┘
                            ▼
                   Relationship graph
            (dots = people/teams/docs/tasks,
             lines = manages/owns/member_of;
             follow the lines to find a path)
                            │
                heavy to store & keep in sync
                            ▼
                       Predicate
          (replace each link with a quick yes/no
           question asked on live data, OR them together)
                            │
                     a decision lands as
                            ▼
            Table / column / row filtering
      (hide a table · mask a column · WHERE-filter rows)
                            │
                       all of this IS
                            ▼
                         ReBAC
            (allowed ⇔ a path connects you
             to the resource — derived, self-updating)
```

- **Authorization (access control)** — Deciding **what an already-logged-in user is allowed to do**. Distinct from *authentication* (proving who you are). The question is always "subject → action → resource: allow or deny?".
- **RBAC (Role-Based Access Control)** — Looks at **the user only**. Decide from a **label granted to the user**: bundle permissions into **roles** (`admin`, `editor`, `viewer`), assign roles to users, allow if the user holds a role that grants the action. *Example:* Alan has the `editor` role, so he can edit **any** post on the site — the rule looks only at his role, never at which post it is.
- **ABAC (Attribute-Based Access Control)** — Looks at **the thing being touched too**, not just the user. Decide by **comparing details of the user with details of the specific resource** — the case RBAC can't handle. ABAC's limit: ABAC can only compare **direct details** of the two, not relationships that run **through other things** (e.g. "a post in a project you belong to"). *Example:* the rule "you may edit a post only if you wrote it" lets Alan edit **his own** posts but not Chloe's.
- **Relationship graph** — Picture a big map of who's connected to what: people, teams, documents, and tasks are the **dots**, and the **lines** between them are relationships like *manages*, *is a member of*, *owns*, or *contains*. Your company's org chart plus all the "who owns what" links *is* this map. Each line is just one simple fact you write down, like "Bob can edit document X." To check whether someone's allowed, you start at the person and **follow the lines** to see if you can reach the thing they want — e.g. *Alan manages Chloe, Chloe is in ProjectAlpha, and ProjectAlpha contains Task#42*, so Alan can reach Task#42. It's just tracing a route from one dot to another.
- **Predicate** — The relationship graph is powerful but heavy: you have to **build and store the whole map**, keep every line up to date as people move teams or hand off documents, and walk it for each request — extra machinery (often a separate graph database) that's easy to get out of sync. And `/librarian` doesn't actually need all that, because most checks only follow **one short link** ("did *you* write this?", "do *you* manage this person?"), not a long chain. So instead of storing the map, `/librarian` replaces each link with a small yes/no question you can ask on the spot and reuse anywhere — like "is this your own row?", "is this person someone you manage?", or "is anyone logged in at all?". Nothing to store or keep in sync — you just ask the question against the live data the moment you need an answer, and string a few together with "or" so that passing *any one* lets you through. Same idea as following lines on the graph, just far lighter. *Example:* to see a salary row, the rule is "is it your own salary?" *or* "are you this person's manager?" — Alan passes for his own pay and for Chloe's (he manages her), but not for a stranger's.
- **Table / column / row filtering** — Once a predicate has decided what you're allowed to see, the answer can apply at three different "zoom levels" of a database table. Think of a table as a spreadsheet: the **whole sheet**, its **columns** (the vertical fields like *name*, *email*, *salary*), and its **rows** (one record per line, like one employee).
  - **Table level** — hide the entire sheet so you don't even know it exists. *Example:* a regular employee querying the database never sees the `audit_logs` or `salaries` table at all — to them it simply isn't there.
  - **Column level** — let you see the sheet, but blank out or mask sensitive columns. *Example:* Alan can open the `employees` table and read everyone's name and department, but the `salary` column comes back as `***` for everyone except himself.
  - **Row level** — let you see the sheet and all its columns, but only the rows that belong to you. This is done with a SQL **`WHERE` clause** — the part of a query that keeps only rows meeting a condition. The system quietly tacks an extra condition onto your query (e.g. `WHERE team = 'Chloe's team'`), so even if you asked for *every* row, the database hands back only the ones that pass. *Example:* Chloe opens the `tasks` table and sees only the tasks assigned to her team, not the whole company's — because a `WHERE team = her team` filter was silently added before the query ran.

  These stack together: a single request might hide some tables outright, mask a column or two on the tables you *can* see, and trim the rows down to just yours — so two people running the *exact same query* get very different results.
- **ReBAC (Relationship-Based Access Control)** — The model that ties everything above together: you're allowed to touch something **only if there's a chain of relationships connecting you to it**. RBAC asked "what role do you have?", ABAC asked "do your details match this thing's details?", and ReBAC asks "**is there a path from you to this thing?**" — following the lines on the relationship graph (or, in `/librarian`, chaining predicates) to find out. The big win is that permissions aren't written down case by case; they're **worked out from the relationships you already have**, so they fix themselves the moment those relationships change.
  - *Direct link:* "you wrote this post" → you can edit it. The moment Alan writes a post, the right to edit it exists automatically — nobody grants it.
  - *One-hop link:* "you manage this person" → you can see their salary. Alan manages Chloe, so he sees Chloe's pay; the day Chloe moves to another manager, Alan loses that access on his own — no one has to remember to revoke it.
  - *Multi-hop link:* "you're on a team that owns the project this task belongs to" → you can edit the task. The permission rides along a chain (*you → team → project → task*) instead of a label you were handed.
  - *Contrast:* in RBAC you'd invent a fresh role for each of these ("post-owner", "salary-of-my-reports", "task-of-my-projects") and keep assigning and revoking them by hand — ReBAC just reads the relationships that are already there.

### Concrete example
Three users ask `/librarian` the **same** question — *"How much did we spend on reimbursements?"* — and ReBAC predicates rewrite the SQL differently for each. The three permission tables (real seed rows for `reimbursement_workflow`) drive the rewrite:

```
semantic_tables  (table gating)   default_read_rule:
   self(employee_username) OR manager_of(employee_username) OR whitelist:reimbursement-workflow
   → 'self' hits for everyone, so the table is VISIBLE to all three users.

semantic_columns (column masking) two registered columns, both unrestricted:
   employee_username  visible_if: any_authenticated  → keep
   amount             visible_if: any_authenticated  → keep
   → no sensitive column here, so the LLM sees the same schema for all three (masking is a no-op).

LLM generates the same base query for everyone (built from the kept columns):
   SELECT SUM(amount) FROM reimbursement_workflow

permission_rules (row filtering)  SAME procedure for all three, applied to the rule above:
   Step 1  user-level predicate first — whitelist match? → FULL access, skip row filter (short-circuit)
   Step 2  else OR every matching row-filter predicate (self, manager_of) into a WHERE
   (resolving a matched predicate may cost one lookup, done once when UserContext is built)

   Binh   (regular employee)
      Step 1  whitelist ✗ → no short-circuit
      Step 2  self ✓ (no lookup)   manager_of ✗
      → WHERE employee_username = 'binh'                        → own claims only

   Chloe  (manages binh,david,emma)
      Step 1  whitelist ✗ → no short-circuit
      Step 2  self ✓ (no lookup)
              manager_of ✓ → lookup: SELECT username FROM employees
                             WHERE manager_username = 'chloe'  → ['binh','david','emma']
      → WHERE employee_username = 'chloe'
              OR employee_username IN ('binh','david','emma')   → self + direct reports

   Alan   (whitelisted)
      Step 1  whitelist ✓ → lookup: EXISTS (SELECT 1 FROM user_whitelist
                            WHERE username = 'alan' AND erp_endpoint = 'reimbursement-workflow')
              → FULL access, short-circuit (self / manager_of never evaluated)
      → (unchanged)                                             → whole company
```

So all three tables act here, each at a different granularity: **`semantic_tables`** gates the table (visible to all), **`semantic_columns`** decides the columns (here both `keep`, so identical for everyone — masking only bites on tables with sensitive fields like salary or HKID), and **`permission_rules`** injects the per-user `WHERE`. The users diverge **only** at the row level — purely because different relationships connect them to the rows.

`manager_of(employee_username)` compiles to `employee_username IN (SELECT username FROM employees WHERE manager_username = :me)` — a one-hop graph traversal expressed as a subquery. Each predicate is a node-to-node edge check; the combined `WHERE` clause *is* the set of permitted paths. Notice nobody got a new role — the difference is purely which relationships connect them to the rows.

### Where you'll meet it
- **Google Zanzibar** — Google's global authz system; the paper that popularized ReBAC. Powers Drive/YouTube/Cloud sharing.
- **OpenFGA** (CNCF) and **SpiceDB** (AuthZed) — open-source Zanzibar implementations; you write a schema and store `object#relation@user` tuples.
- **GitHub / Google Drive permissions** — "you can edit this file because you're in the team that owns the folder" is textbook ReBAC.
- **AWS IAM resource policies, Notion, Slack** — increasingly mix ReBAC-style relationship checks into their authorization.
- This **ERP `/librarian` endpoint** — ReBAC predicates expressed as SQL subqueries instead of a graph engine.

### Common confusions
- **ReBAC vs RBAC** — RBAC asks "does the user hold the right *role*?"; ReBAC asks "is there a *relationship path*?". A role is global; a relationship is specific to a user–resource pair.
- **ReBAC vs ABAC** — ABAC compares *attributes* against a policy ("dept matches"); ReBAC follows *edges* between entities. They compose: OpenFGA adds attribute conditions on top of relationships.
- **ReBAC vs ACL** — an Access Control List is a flat per-resource list of who's allowed; ReBAC *derives* that list from relationships, so it stays correct as the graph changes (remove someone from a team and all their inherited access disappears at once).
- **ReBAC ≠ a graph database** — ReBAC is the *model*; a graph DB is one *implementation*. `/librarian` does ReBAC with plain Postgres subqueries — no graph engine.
