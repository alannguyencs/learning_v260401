## ReBAC (Relationship-Based Access Control)

**In one sentence:** ReBAC is an authorization model that decides "can this user touch this resource?" by asking **whether a relationship path connects them** in a graph (e.g. *you manage the person who owns this record*), rather than by checking a static role — which is exactly how the `/librarian` natural-language-to-SQL agent guards every database read.

### Key terminologies
These build on each other; read top to bottom and the last term (ReBAC) falls out naturally.

- **Authorization (access control)** — Deciding **what an already-logged-in user is allowed to do**. Distinct from *authentication* (proving who you are). The question is always "subject → action → resource: allow or deny?".
- **RBAC (Role-Based Access Control)** — Decide from a **label granted to the user ahead of time**: bundle permissions into **roles** (`admin`, `editor`, `viewer`), assign roles to users, allow if the user holds a role that grants the action.
- **ABAC (Attribute-Based Access Control)** — Decide at **request time by evaluating a rule over the properties of *both* the user and the specific resource** (plus context). Because the rule sees the resource, it can *compare* them — the case RBAC can't express. Flexible, but it only compares **flat properties**; it stalls on *chained* relationships (e.g. "a post in a project you belong to"), which are paths through other entities rather than properties of the resource itself.

  > **The same task, "edit your own post," in all three models:**
  > - **RBAC** — "Is `editor` in your roles?" Looks at the **user only**, ignores the post → can't restrict to *your own*; an editor edits everyone's.
  > - **ABAC** — "Is `post.author_id == user.id`?" Compares **user vs. this post's attributes** at request time → "your own" works.
  > - **ReBAC** — "Is there a `created` edge from you to this post (or a path *you → team → project → post*)?" Follows **relationships/paths**, so even indirect ownership works.
- **Relationship graph** — A graph whose **nodes** are entities (users, teams, documents, tasks) and whose **edges** are relationships (`manages`, `member_of`, `owns`, `contains`). The org chart plus ownership links *is* this graph.
- **Path / graph traversal** — A connected sequence of edges from one node to another (`alan → manages → chloe → member_of → ProjectAlpha → contains → Task#42`). Traversal is walking those edges to discover whether a path exists — the same idea as BFS/DFS you saw in a data-structures course.
- **Relationship tuple** — In full ReBAC engines, a relationship is stored as one row of the form `<object>#<relation>@<user>`, e.g. `document:X#editor@bob` ("Bob is an editor of document X"). The whole permission state is just a big set of these tuples.
- **Predicate** — A small, named, reusable boolean test for one relationship, e.g. `self(column)`, `manager_of(column)`, `whitelist:endpoint`, `any_authenticated`. A rule is predicates combined with `OR`; each predicate compiles to a concrete SQL condition at runtime. This is `/librarian`'s lightweight stand-in for storing tuples in a graph database.
- **Table / column / row filtering** — The three granularities at which an access decision can act on tabular data: hide a whole **table** (you can't see it exists), **mask/strip a column** (e.g. salary → `***`), or **filter rows** (inject a `WHERE` so you only get your own / your team's rows).
- **ReBAC (Relationship-Based Access Control)** — The model that grants access **iff a permitted relationship path exists** between user and resource. Permissions are *derived* from relationships, so they update automatically when the org graph changes — no per-case role to maintain.

### How these terms are related
Read this as a cause-and-effect chain — each step forces the next:

1. **Authentication → authorization.** Once a user is *identified*, the system still has to decide *what they may do*. That second decision is access control.
2. **RBAC → role explosion.** The first answer is to attach permissions to roles. But "managers see their own reports' leave, finance sees everyone's, you see your own" needs a fresh role per relationship — the role count blows up.
3. **ABAC → still can't chain.** Attributes/policies handle conditions ("only during work hours") but struggle with **transitive** relationships like "a task in a project I belong to" — that's a path, not a single attribute comparison.
4. **Paths → model it as a graph.** Both pain points are really "permission should follow relationships." So represent entities and their links as a **relationship graph**.
5. **Graph → traversal answers the question.** "Can Alan see Task #42?" becomes "is there a permitted **path** from Alan to Task #42?" — solved by **graph traversal**, not a role lookup. That is ReBAC.
6. **Traversal → store the edges.** To traverse, you store the edges. Full engines store them as **relationship tuples** (`object#relation@user`) in a dedicated database (Google Zanzibar, OpenFGA, SpiceDB).
7. **Tuples are overkill at small scale → predicates.** For a ~20-person ERP, `/librarian` skips the graph DB: it expresses each relationship as a **predicate** that derives the edge from tables it already has (`employees.manager_username`, `task_team_members`, `user_whitelist`) and compiles to a SQL subquery.
8. **Predicates → three-level enforcement.** Evaluating a table's rule against the user yields a decision the engine applies as **table gating, column masking, or row filtering** — so one `/librarian` endpoint can translate any question to SQL while never returning a row (or even a column name) the user isn't related to.

**The chain in one line:**
`authorization → RBAC (role explosion) → ABAC (can't chain) → relationship graph → path traversal = ReBAC → tuples / predicates → table+column+row filtering`

### Concrete example
Three users ask `/librarian` the **same** question — *"How much did we spend on reimbursements?"* — and ReBAC predicates rewrite the SQL differently for each. The three permission tables (real seed rows for `reimbursement_workflow`) drive the rewrite:

```
semantic_tables  (table gating)   default_read_rule:
   self(employee_username) OR manager_of(employee_username) OR whitelist:reimbursement-workflow
   → 'self' hits for everyone, so the table is VISIBLE to all three users.

semantic_columns (column masking) two registered columns, both unrestricted:
   employee_username  visible_if: any_authenticated  → keep
   amount             visible_if: any_authenticated  → keep
   → no sensitive column here, so the LLM sees the same schema for all three (masking is a no-op).

LLM generates the same base query for everyone (built from the kept columns):
   SELECT SUM(amount) FROM reimbursement_workflow

permission_rules (row filtering)  SAME procedure for all three, applied to the rule above:
   Step 1  user-level predicate first — whitelist match? → FULL access, skip row filter (short-circuit)
   Step 2  else OR every matching row-filter predicate (self, manager_of) into a WHERE
   (resolving a matched predicate may cost one lookup, done once when UserContext is built)

   Binh   (regular employee)
      Step 1  whitelist ✗ → no short-circuit
      Step 2  self ✓ (no lookup)   manager_of ✗
      → WHERE employee_username = 'binh'                        → own claims only

   Chloe  (manages binh,david,emma)
      Step 1  whitelist ✗ → no short-circuit
      Step 2  self ✓ (no lookup)
              manager_of ✓ → lookup: SELECT username FROM employees
                             WHERE manager_username = 'chloe'  → ['binh','david','emma']
      → WHERE employee_username = 'chloe'
              OR employee_username IN ('binh','david','emma')   → self + direct reports

   Alan   (whitelisted)
      Step 1  whitelist ✓ → lookup: EXISTS (SELECT 1 FROM user_whitelist
                            WHERE username = 'alan' AND erp_endpoint = 'reimbursement-workflow')
              → FULL access, short-circuit (self / manager_of never evaluated)
      → (unchanged)                                             → whole company
```

So all three tables act here, each at a different granularity: **`semantic_tables`** gates the table (visible to all), **`semantic_columns`** decides the columns (here both `keep`, so identical for everyone — masking only bites on tables with sensitive fields like salary or HKID), and **`permission_rules`** injects the per-user `WHERE`. The users diverge **only** at the row level — purely because different relationships connect them to the rows.

`manager_of(employee_username)` compiles to `employee_username IN (SELECT username FROM employees WHERE manager_username = :me)` — a one-hop graph traversal expressed as a subquery. Each predicate is a node-to-node edge check; the combined `WHERE` clause *is* the set of permitted paths. Notice nobody got a new role — the difference is purely which relationships connect them to the rows.

### Where you'll meet it
- **Google Zanzibar** — Google's global authz system; the paper that popularized ReBAC. Powers Drive/YouTube/Cloud sharing.
- **OpenFGA** (CNCF) and **SpiceDB** (AuthZed) — open-source Zanzibar implementations; you write a schema and store `object#relation@user` tuples.
- **GitHub / Google Drive permissions** — "you can edit this file because you're in the team that owns the folder" is textbook ReBAC.
- **AWS IAM resource policies, Notion, Slack** — increasingly mix ReBAC-style relationship checks into their authorization.
- This **ERP `/librarian` endpoint** — ReBAC predicates expressed as SQL subqueries instead of a graph engine.

### Common confusions
- **ReBAC vs RBAC** — RBAC asks "does the user hold the right *role*?"; ReBAC asks "is there a *relationship path*?". A role is global; a relationship is specific to a user–resource pair.
- **ReBAC vs ABAC** — ABAC compares *attributes* against a policy ("dept matches"); ReBAC follows *edges* between entities. They compose: OpenFGA adds attribute conditions on top of relationships.
- **ReBAC vs ACL** — an Access Control List is a flat per-resource list of who's allowed; ReBAC *derives* that list from relationships, so it stays correct as the graph changes (remove someone from a team and all their inherited access disappears at once).
- **ReBAC ≠ a graph database** — ReBAC is the *model*; a graph DB is one *implementation*. `/librarian` does ReBAC with plain Postgres subqueries — no graph engine.
