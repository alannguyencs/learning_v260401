## vLLM

**In one sentence:** vLLM is a high-throughput **serving engine** for large language models whose key trick, **PagedAttention**, manages a model's KV cache the way an operating system manages RAM with paging — so one GPU can serve far more requests at once.

### Key terminologies
These build on each other; read top to bottom and the last term (vLLM) falls out naturally.

- **Large Language Model (LLM)** — A transformer neural network (Llama, GPT-style) that generates text **one token at a time**, each new token conditioned on all previous ones.
- **Token** — The small unit of text an LLM reads and emits — usually a word piece (e.g. `"paging"` → `pag` + `ing`). It's the model's input/output unit, but attention never works on tokens directly, only on the vectors derived from them; generation is a loop that emits one token per step, and a length-**N** sequence is N tokens, so attention's cost grows with N.
- **Attention** — The transformer mechanism by which each token "looks back" at earlier tokens — comparing itself against every other token — to decide what to focus on and generate next. For N tokens that's N×N comparisons (the core source of cost), and each new token needs all earlier tokens' representations.
- **Key / Value vectors** — The per-token **key** and **value** float vectors that attention reads (both derived from a token's embedding — not the token itself). The **key** is matched against a query via dot product to decide *how much* attention each token gets; the **value** is the payload those weights sum over to decide *what* information is passed on.
- **KV cache (Key–Value cache)** — Instead of recomputing every past token's key/value vectors on each step, the model **saves them** and reuses them. That saved store is the KV cache; it grows by one slot per generated token and lives in GPU memory.
- **GPU memory / VRAM** — The GPU's main on-board memory (the advertised "40 GB" / "80 GB"), holding the model weights *and* every active request's KV cache. Fast versus CPU RAM but comparatively **slow** versus on-chip SRAM (~1.5–3 TB/s), and limited — when it fills up you must drop requests or shrink the batch, so VRAM is the scarce resource. Hardware folks call it **HBM (High-Bandwidth Memory)**.
- **Fragmentation** — When chunks of memory are allocated and freed in different sizes over time, the free space breaks into gaps too small to reuse. Total free memory looks large, but no single **contiguous** block is big enough — so capacity is wasted.
- **Virtual memory / paging (OS concept)** — The OS trick where a program sees one big continuous address space, but the OS splits it into fixed-size **pages** mapped to scattered physical RAM **frames** via a **page table**. This is exactly the idea vLLM borrows.
- **PagedAttention** — vLLM's attention implementation that splits each sequence's KV cache into fixed-size **blocks (pages)**, stores them wherever VRAM has room, and uses a block table (a page table) to find them — eliminating fragmentation.
- **vLLM** — The open-source LLM **serving engine** built around PagedAttention (plus continuous batching). It runs other people's models for high-throughput, multi-user inference.

### How these terms are related
Read this as a cause-and-effect chain — each step forces the next:

1. **LLM → token-by-token generation.** An LLM produces text one token at a time, so it runs the same forward step in a loop.
2. **Generation → attention → needs past tokens.** Each step's attention must look back at every earlier token's key/value vectors.
3. **"Don't recompute" → KV cache.** Recomputing those vectors every step is wasteful, so the model stores them once in the **KV cache**.
4. **KV cache → lives in VRAM, and it's big.** The cache sits in **GPU memory** and grows with every token; many users or long prompts make the total KV cache huge and fill VRAM.
5. **Contiguous per-request layout → fragmentation.** If each sequence's KV cache is one contiguous slab, and sequences start, stop, and grow at different times, **GPU memory fragments** — you fit far fewer requests than the raw GB count suggests (older systems wasted 60–80%).
6. **Fragmentation → borrow virtual memory.** vLLM applies the OS **paging** idea: break each KV cache into fixed-size **blocks** and place them wherever there's free VRAM, tracked by a block (page) table.
7. **Paging → PagedAttention implements it.** The attention kernel no longer assumes one contiguous KV buffer; **PagedAttention** walks the blocks via the mapping to fetch keys/values.
8. **PagedAttention → vLLM's win.** Tightly packing blocks from many sequences cuts waste to under ~4%, so the GPU holds many more concurrent requests — **2–4× higher throughput** (up to 14–24× vs. vanilla Hugging Face Transformers) at similar latency, especially for long sequences.

**The chain in one line:**
`LLM → attention → KV cache → GPU memory → fragmentation → virtual memory (paging) → PagedAttention → vLLM (higher throughput & concurrency)`

### Concrete example
Serve a Hugging Face model with vLLM as an OpenAI-compatible API:

```bash
pip install vllm
vllm serve meta-llama/Llama-3.1-8B-Instruct
```

```python
from openai import OpenAI
client = OpenAI(base_url="http://localhost:8000/v1", api_key="EMPTY")

resp = client.chat.completions.create(
    model="meta-llama/Llama-3.1-8B-Instruct",
    messages=[{"role": "user", "content": "Explain paging in one sentence."}],
)
print(resp.choices[0].message.content)
```

Now picture 500 users hitting that endpoint at once. Each user's growing **KV cache** is chopped into **blocks** scattered across **VRAM**; **PagedAttention** uses the block table to read them during **attention**; because there's almost no **fragmentation**, all 500 sit on the GPU together instead of being turned away. Every term in the list above is doing its job in that one request flow.

### Where you'll meet it
- **vLLM project** (`github.com/vllm-project/vllm`) — a widely-used open-source / PyTorch Foundation project.
- **LMSYS Chatbot Arena / FastChat** — used vLLM for up to 30× more throughput and half the GPUs (~30k requests/day).
- **Red Hat, NVIDIA, and cloud providers** ship vLLM as a standard self-hosted inference backend.
- Any team **self-hosting open-weights models** (Llama, Mistral, Qwen) instead of a paid hosted API.

### Common confusions
- **vLLM vs. the model** — vLLM is the *engine that runs* models, not a model itself. The "v" means *virtual* (as in virtual memory), not a version.
- **PagedAttention vs. FlashAttention** — FlashAttention speeds up the attention *computation*; PagedAttention optimizes how the KV cache is *stored*. Different problems, often used together.
- **KV cache vs. model weights** — both live in VRAM, but weights are fixed and shared across all requests; the KV cache is per-request and grows as text is generated.
- **vLLM vs. Ollama / TGI / TensorRT-LLM** — all serve LLMs, but vLLM targets high-throughput multi-user serving; Ollama targets easy single-user local use; TGI and TensorRT-LLM are competing engines.
