# Full-Stack Web Application

Alright everyone, settle in, because today we're going to build a whole web application out loud — not by writing every line, but by walking the chain of ideas that makes one. And I want you to notice something as we go: each piece we add exists because the piece before it left a gap. Nothing in this stack is arbitrary. By the end, when I say the words **full-stack web application**, you should hear the whole machine humming, from the pixel Chloe clicks to the row that lands in the database on Alan's server.

So let's start at the very bedrock, because everything else is built on it. The web runs on the **client–server model**. A **client** — that's the browser in front of Chloe — sends a request, and a **server** — that's the backend Alan wrote — receives that request, does some work, and sends a response back. The crucial thing, the thing I want you to burn into memory, is that neither side trusts the other's memory. Every request stands completely alone. When Chloe opens the app, her browser shouts a question across the internet — "give me Chloe's profile" — and the server does the work and shouts the answer back. They never share a brain. The next time Chloe wants something, her browser has to ask all over again, from scratch.

```
browser (client) ──request──> server
browser (client) <─response── server   (every request stands alone)
```

But the moment you say "the browser shouts a question across the internet," you've created a problem you have to solve immediately: *how* does that shout travel? Two separate machines need an agreed way to carry messages, and that's where **HTTP** comes in. **HTTP**, the HyperText Transfer Protocol, is just the rulebook for the request-and-response messages — it's the **transport** that carries everything else we'll talk about today. Now, plain **HTTP** has a fatal flaw: anyone sitting on the same network can read it or tamper with it. So in production we wrap it. **HTTPS** is the exact same protocol, but wrapped in **TLS** (Transport Layer Security) **encryption**, so the messages are scrambled in transit and the server's identity is proven by a **certificate** — the `S` literally stands for "Secure." Picture Chloe logging in from a café. Over plain `http://`, anyone on that café Wi-Fi could read her password in clear text. Over `https://`, that same message turns into gibberish for everyone except Alan's server, and the little padlock in her address bar means the certificate proved she's really talking to *his* server and not an impostor. That's why cookies, tokens, and passwords must never, ever travel over plain HTTP.

```
HTTP   = the transport (readable by anyone on the network)
HTTPS  = HTTP + TLS encryption + certificate  (scrambled, identity proven)
```

Now here's where the transport runs out of road. HTTP faithfully carries the bytes, but it doesn't tell the two sides what those bytes are supposed to *mean*. The browser and server still need to agree on a grammar. That agreement is the **REST API** (Application Programming Interface). REST stands for REpresentational State Transfer, and it's just a convention for the conversation: you use plain HTTP verbs — `GET` to read, `POST` to create, `PUT` or `PATCH` to update, `DELETE` to remove — on **URLs that name resources**, and you usually pass **JSON** (JavaScript Object Notation) back and forth. When Chloe's browser wants her profile, it sends `GET /api/profiles/chloe`. When she posts a new note, it sends `POST /api/notes` with the note's text as JSON. "GET means fetch, POST means create" — that shared rulebook *is* the **REST API**. It's the grammar both sides promise to speak.

```
GET    /api/notes      → read
POST   /api/notes      → create
PUT    /api/notes/1    → update
DELETE /api/notes/1    → remove
```

Now, REST has one assumption baked in: Chloe *asks*, the server *answers*, one request at a time. But sometimes that's not enough. Sometimes the server needs to tell Chloe something the instant it happens, without her asking. That's where a **WebSocket** comes in. A **WebSocket** is a protocol for a persistent, two-way connection — it starts life as an ordinary HTTP request that "upgrades" into a long-lived open pipe, and once that pipe is open, *either* side can push a message at any moment without a fresh request. Think of REST as Chloe asking "any new notes? any new notes?" over and over, while a **WebSocket** is Alan's server keeping a line open to her browser and *shouting* "new note!" the instant one arrives. REST handles her normal save-and-load; the **WebSocket** handles the live chat and the notification badge that lights up in real time. And like HTTP, it has a secure form, `wss://`, over TLS.

```
REST       →  client asks, server answers   (request / wait)
WebSocket  →  open pipe, either side pushes  (real-time)
```

So we have a contract. But a contract is just words until something on the other end actually *answers* the requests. Some program has to receive `GET /api/notes`, run real logic, and reply. In this stack, that program is **FastAPI**. **FastAPI** is a modern Python web framework for building APIs quickly — you write a plain function and decorate it with the route it handles, like `@app.get("/api/notes/{id}")`, and FastAPI takes care of the rest: it validates the incoming data, it runs **async** so it can juggle many requests at once, and it even auto-generates an interactive `/docs` page where Chloe's request can be tried by hand. **FastAPI** is the backend's front door. Now, it's not the only door in town — Python has a whole family of web frameworks. There's **Django**, the batteries-included one with its own ORM and admin UI (User Interface), great when you want a whole templated website. There's **Flask**, the minimal microframework you assemble yourself. There's **Django REST Framework** for building REST APIs on top of Django, and there's **Starlette** and **Litestar**, the async toolkits — **Starlette** being the very thing **FastAPI** is built on. Alan picked **FastAPI** over **Django** because he only needed a JSON API, not a full website, and over **Flask** because he wanted the async speed and automatic validation handed to him for free.

And that phrase — "automatic validation" — points straight at the next piece, because **FastAPI** doesn't do that part by itself. It leans on **Pydantic**. **Pydantic** is the Python data-validation library that **FastAPI** is built on. You declare the *shape* of your request and response bodies as typed Python classes — we call these **schemas** or **DTOs** (Data Transfer Objects) — and **Pydantic** automatically checks every incoming JSON payload against that shape, rejecting anything malformed with a clear error, and serializing your outgoing objects back into JSON. It's the thing that turns loose, untrustworthy JSON into clean, typed objects. Alan declares a `NoteIn` schema with a single field, `text: str`. When Chloe POSTs a note, **Pydantic** confirms that `text` really is a string, and if she somehow sends a number, **Pydantic** rejects the request with a `422` before Alan's code ever runs. So his handler never has to hand-check the input — it just receives a clean `NoteIn` object and gets to work.

```
raw JSON  ──Pydantic schema check──>  clean typed object  (or 422 rejected)
```

Now slow down here, because there's a category of work that shouldn't live inside any single handler. Think about checking who's logged in, or stamping the right security headers, or logging every request. You do *not* want to copy-paste that into every endpoint. So we reach for **middleware**. **Middleware** is code that sits between the request arriving and your route handler running — it wraps *every* request, so it can act on all of them in one place, and each piece can run logic on the way **in** and again on the way **out**. Before any of Alan's route functions fire, a **middleware** layer peeks at Chloe's cookie to figure out who she is, and another stamps the security headers her browser needs. Written once, applied to every endpoint automatically.

```
request ─> [ middleware: auth, logging, headers ] ─> route handler ─> response
```

One of the most important jobs **middleware** handles there is **CORS**, and CORS deserves a real pause because it confuses everyone at first. **CORS**, Cross-Origin Resource Sharing, is a browser security rule. By default, a page loaded from one **origin** — and an origin is the combination of scheme plus domain plus port, like `http://localhost:3999` — is *blocked* from calling an API on a *different* origin, like `http://localhost:8999`. The server has to explicitly opt in by sending an `Access-Control-Allow-Origin` header naming who's allowed in, and that's almost always configured as **middleware**. Why does this rule exist? To protect users. Chloe's React app runs on port 3999, but Alan's API lives on port 8999 — different origins — so her browser refuses the call until Alan's **CORS** middleware adds a header saying "3999 is allowed." And that same rule is what stops a random evil website from quietly hitting Alan's API using Chloe's logged-in cookie: the browser simply won't let it cross origins without permission.

```
page @ :3999  ──calls──>  API @ :8999   ✗ blocked (different origin)
API sends "Access-Control-Allow-Origin: :3999"  →  ✓ allowed
```

Good. The backend can now receive requests, validate them, and gate them. But the handler still has to *do* something — and almost always that means reading or writing data that has to survive. Here we hit a famous mismatch. In Alan's code, `chloe.bestFriend` is a pointer to another object. But in the database, that same relationship is just a number sitting in a column. Those two worlds don't line up, and hand-writing the SQL (Structured Query Language) to bridge them — then stuffing the results back into objects — is tedious and error-prone. So we use an **ORM**. **ORM** stands for Object–Relational Mapping, and it's the general technique — and the kind of library that implements it — for bridging objects in code and rows in a relational database. You work with classes and objects, and the **ORM** auto-generates the SQL to load and save them. The **ORM** is the translator that reconciles the mismatch automatically, so Alan never hand-stuffs a column into an object again. And notice — the **ORM** is an *idea*, language-agnostic; every language has its own.

```
objects in code   ⇄   ORM (translator)   ⇄   rows in tables
```

The **ORM** is the technique; now you have to pick a concrete one for Python, and in this stack that's **SQLAlchemy**. **SQLAlchemy** is Python's most popular ORM implementation. Instead of writing raw SQL strings, you define Python classes that mirror your tables, and **SQLAlchemy** translates a call like `session.query(User)` into `SELECT ... FROM users` and translates the rows back into Python objects. When Alan writes `note = Note(text="hi")` and `session.add(note)` in plain Python, **SQLAlchemy** quietly turns that into the `INSERT INTO notes ...` that the database actually understands. Alan gets to think in objects; **SQLAlchemy** thinks in SQL.

But **SQLAlchemy** only *translates* — it doesn't store anything. The bytes still have to live somewhere durable, and that somewhere is **PostgreSQL**. **PostgreSQL** is a free, industrial-strength relational database: data lives in tables of rows and columns, related tables are joined by keys, and every change is protected by transactions that are all-or-nothing. **PostgreSQL** is where the real, permanent truth sits. Every note Chloe has ever written is a row in a `notes` table inside **PostgreSQL**, and her account is a row in a `users` table linked to those notes by her user id. She can close the browser, Alan can reboot the server — the rows are still sitting there, safe. That's the whole point of **PostgreSQL**: it remembers.

```
SQLAlchemy  →  generates SQL  →  PostgreSQL  →  durable rows (survives reboot)
```

So now the entire backend exists — it can receive a request, validate it, gate it, and persist data. But here's the thing: an API that returns JSON is completely useless to Chloe as a human. She can't read raw JSON. Something has to turn that data into a screen she can see and click, and that's the frontend's job. The modern way to build it is as an **SPA**, a Single-Page Application. In an **SPA**, the browser loads *one* HTML (HyperText Markup Language) page exactly once, and from then on JavaScript rewrites the content in place as Chloe navigates — fetching fresh data over the API instead of asking the server for a whole new page on every click. The result feels like a desktop app, with no jarring full-page reloads. When Chloe clicks from her note feed to her profile, the page doesn't blank out and reload — the content just swaps, and her profile JSON loads quietly in the background. The URL still changes, but it's been one continuous page the whole time. The old model, where every single click fetched a brand-new HTML page, is what the **SPA** replaced — and the **SPA** is precisely *why* we'll need client-side routing and a dev proxy in a moment.

```
SPA  →  load ONE page once  →  JS swaps content in place  (no full reloads)
```

But what actually does that swapping? That's **React 18**. **React** is a JavaScript frontend tool for building user interfaces out of reusable **components** — self-contained little pieces of UI. **React** keeps a virtual copy of the page in memory and, when the data changes, re-renders only the part that actually changed, so the screen always reflects the current **state**. The little `<NoteCard>` box that displays one note is a **React** component; render it once per note and you've got Chloe's whole feed. When she deletes a note, **React** notices the data changed and silently redraws just that one card — not the whole page. Now, a fine point worth flagging: **React** technically calls itself a *library* rather than a full framework, because you assemble the surrounding tools yourself — but in everyday speech it's spoken of as *the* frontend framework of this stack. And like the backend, it has siblings: **Vue** with its gentle template-based learning curve, **Angular** the heavyweight batteries-included framework, **Svelte** that compiles itself away at build time, **SolidJS** with React-like syntax and finer-grained updates, and meta-frameworks built *on top* of React like **Next.js** and **Remix**. Alan picked **React** over **Angular** because he wanted a lightweight library he could pair with his own tools, and over **Vue** and **Svelte** mostly for its huge ecosystem and hiring pool.

But raw **React** code can't ship straight to the browser — it has to be run during development and packaged for production. That's the job of **Vite**. **Vite** is a fast frontend build tool and dev server. During development, **Vite** serves your React code to the browser instantly, with no slow rebuild every time you save; for production, **Vite** bundles everything into small, optimized files. While Alan edits a button's color, **Vite** updates it in the browser the instant he hits save — no waiting. When it's time to ship, **Vite** squashes all the React files into a few tiny ones the browser can download in a blink. **Vite** is the engine that runs and packages the frontend, and it replaced the older Create-React-App tooling.

And **Vite** quietly solves one more problem for us — remember **CORS**? During local development, Chloe's React app lives on port 3999 and the API on port 8999, which are different origins, which would trip **CORS** on every single call. So **Vite** runs a **dev proxy**. A **dev proxy** is a development-only shortcut: the frontend dev server forwards API calls — paths like `/api/*` — to the backend on its different port, so that to the browser, everything *appears* to come from one origin, and **CORS** never trips. In dev, Chloe's app on 3999 calls `/api/notes`, the **dev proxy** quietly relays it to the backend on 8999 and hands the answer back, and the browser thinks it never left port 3999. Here's the neat symmetry: **CORS** is the server *granting* cross-origin permission, while the **dev proxy** *avoids being cross-origin* in the first place. And it exists only locally — in production, a real reverse proxy does the same routing.

```
CORS       →  server grants cross-origin permission
dev proxy  →  makes frontend + API look like ONE origin (no crossing at all)
```

Now the UI works, but it looks like raw, unstyled HTML — and styling it by hand is tedious. That's where **Tailwind CSS** earns its place. **Tailwind** is a utility-first CSS (Cascading Style Sheets) framework: instead of writing separate stylesheets and inventing class names, you style an element by stacking tiny single-purpose classes right in the markup, like `class="flex gap-2 rounded bg-blue-500 p-4"`. To make Chloe's note cards rounded, padded, and blue, Alan just sprinkles `rounded p-4 bg-blue-500` onto the element — he never flips over to a separate `.css` file to dream up a name like `.note-card-wrapper`. Styling happens inline, fast.

So now both halves exist — a full backend and a full frontend. And that raises a practical question: where do you keep all this code? The answer in this stack is a **monorepo**. A **monorepo**, short for mono-repository, means keeping the backend, the frontend, and the shared config together in *one* Git repository instead of two. One clone, one version history, one place to change an API and its UI together. Alan's `backend/` and `frontend/` folders sit side by side in a single repo, so when he renames a field in the API, he fixes the server code and the React code that reads it in the *same commit* — they can never drift apart because they ship together. Now, here's a distinction I really want you to hold onto, because people muddle it constantly: **monorepo** is a *different axis* from "full-stack." *Full-stack* describes how many *layers* you build — front, back, and database, a matter of **scope**. *Monorepo* describes how many *repos* you store them in — a matter of **code layout**. They're independent. Alan's app happens to be both full-stack and a monorepo, but he could have kept it full-stack while splitting the backend and frontend into two separate repos.

```
full-stack  →  how many LAYERS you own   (scope)
monorepo    →  how many REPOS you store   (code layout)   — independent axes
```

There's still a gap, though. The server is stateless — remember the very first idea, that every request stands alone? That means on each new request, the server has no idea who's calling. We need a way for Chloe to prove who she is on every single call, and the elegant way this stack does it is **shared-cookie SSO**. **SSO** is Single Sign-On, and the shared-cookie flavor works like this: Chloe logs in once on a main site, the server hands her browser an `HttpOnly` session **cookie** scoped to a shared domain, and every sibling app on that domain trusts that same cookie — so Chloe is automatically logged in everywhere without logging in again. She signs in once on the company's main website, it drops a cookie in her browser, and when she clicks over to the payslip app on the same domain, her browser quietly sends that same cookie along. The app sees it, says "ah, this is Chloe," and never shows a second login screen. That's **shared-cookie SSO**.

But that raises two more questions: what's *inside* that cookie, and how does the login that issues it actually happen? The contents are typically a **JWT**, a JSON Web Token. A **JWT** is a signed, self-contained identity token — a compact string in three parts, `header.payload.signature`, that encodes *who the user is* plus an expiry, and is signed with a secret so the server can verify it wasn't tampered with — *without* looking anything up in a database. When Chloe logs in, the server hands her a **JWT** that effectively says "this is Chloe, valid until 5pm," signed so nobody can forge it. On every later request, her browser sends that **JWT** back, tucked inside the cookie, and the server just re-checks the signature and trusts it — no database hit needed to re-confirm she's still Chloe. That's the whole magic of the **JWT**: the trust travels *with* the token.

```
cookie ──carries──> JWT (header.payload.signature)
server re-checks signature  →  trusts it   (no DB lookup)
```

And the login flow that mints that token in the first place is **OAuth / OIDC**. **OAuth 2.0** is the standard protocol for *delegated authorization* — it lets a user allow one app to act on their behalf at another service *without handing over their password*, by redirecting them to that service and coming back with a token. **OpenID Connect**, or **OIDC**, is a thin layer on top of **OAuth** that adds *authentication* — proving *who* the user is. That's the "Log in with Google" flow you've used a hundred times. Instead of Alan's app ever storing Chloe's password, it bounces her to Google; she approves; Google redirects her back with a signed token saying "this is Chloe," and Alan's app trusts it. Chloe never typed a password into Alan's app at all — that delegation dance is **OAuth**, and the "who is she, exactly" part is **OIDC**.

Now everything works — on Alan's laptop. And "works on my machine" is the oldest curse in software. So the next piece packages each part so it runs identically *anywhere*, and that's **Docker**. **Docker** is a containerization tool that packages an app *together with* its exact dependencies, runtime, and config into a portable **image** that runs the same on your laptop, a teammate's, or production. A running image is called a **container** — lightweight, isolated, but sharing the host OS (operating system) kernel, unlike a full virtual machine. Alan builds one **Docker** image for his FastAPI backend and another for his frontend, and whoever runs them — Chloe's laptop or the production server — gets the exact same Python version, the exact same libraries, the exact same settings. The app behaves identically everywhere, and "works on my machine" stops being an excuse.

```
app + exact deps + runtime + config  →  Docker image  →  runs identically anywhere
```

Finally, building those images and shipping them by hand, every time, would be slow and error-prone — so we automate it with **GitHub Actions CI/CD**. **GitHub Actions** is GitHub's built-in automation, and it covers two things. **CI**, Continuous Integration, auto-runs your linters and tests on every push, so broken code can't merge. **CD**, Continuous Deployment, auto-builds and ships the passing code to a server. You describe the steps in a YAML (YAML Ain't Markup Language) file and GitHub runs them for you. The moment Alan pushes a commit, **GitHub Actions** spins up a fresh machine, runs all the tests, builds the Docker images, and *only* if everything passes does it copy the new code onto the live server — so Chloe gets the update without Alan ever logging into a server by hand.

```
git push  →  GitHub Actions: run tests  →  (if green)  build Docker  →  deploy
```

And *that* — all of it, working together — is the **full-stack web application**. The front of the stack, which is what Chloe sees: React, Vite, Tailwind. The back of the stack, the server and database she never sees: FastAPI, Pydantic, middleware, SQLAlchemy, PostgreSQL. And the plumbing that connects and ships them: HTTPS, REST, the monorepo, shared-cookie SSO carrying a JWT minted by OAuth, all packaged by Docker and deployed by CI/CD. "Full-stack" means Alan owns *every* layer, from the pixel Chloe clicks to the database row that pixel becomes.

Let me make that concrete with one click, the one we've been building toward the whole lesson — Chloe presses "Save note." On the frontend, a **React** component fires a REST call: a `fetch("/api/notes", { method: "POST", ... })` with `credentials: "include"`, and it's that one little flag that tells the browser to attach the **shared SSO cookie**. The button itself is styled with **Tailwind** classes right in the markup, and **Vite** served that component in dev and bundled it for production. The request crosses the **REST** contract over **HTTPS** and lands at Alan's **FastAPI** route, `@app.post("/api/notes")`. There, `current_user` reads the **shared cookie** to confirm it's Chloe; **Pydantic** has already validated the JSON into a clean `NoteIn`; **SQLAlchemy** turns a `Note` object into an `INSERT INTO notes`; **PostgreSQL** stores the row durably; and **FastAPI** returns JSON back across **REST**. One button press, and every single term in today's lesson did its job.

```
React+Tailwind ─POST /api/notes (cookie)→ FastAPI ─Pydantic→ SQLAlchemy ─INSERT→ PostgreSQL
       (Vite bundled it)        (HTTPS/REST)     (current_user reads cookie)        (durable row)
```

Let me leave you with the confusions that trip people up, so you can sidestep them. First, **full-stack** is not a technology — it's a *scope*: back-end means server plus DB (database), front-end means the browser UI, and full-stack means you own both plus the glue. Second, **library versus framework**: React calls itself a library because you assemble the rest yourself, while FastAPI is a framework because it dictates more of the structure — but in practice both are the backbone of their side. Third, **SQLAlchemy is not PostgreSQL**: SQLAlchemy is Python code that *generates* SQL, while PostgreSQL is the actual engine that *runs* it — and the ORM could talk to SQLite instead with barely a change to the Python. Fourth, **Vite is not React**: Vite doesn't build any UI; it's the dev-server and bundler that runs and packages React. Fifth, **shared-cookie SSO versus a JWT-in-a-header**: both prove identity, but a cookie is set and sent automatically by the browser and shared across same-domain apps, while a bearer token is attached manually per request — some stacks use one, some the other, some both. And sixth, **monorepo versus monolith**: a monorepo is one *repository* that may hold separate apps, while a monolith is one *deployed program* — different axes entirely, and you can mix them however you like.

You'll meet this exact stack everywhere, by the way — in Tiangolo's own official Full-Stack FastAPI Template, which is the canonical version of FastAPI plus SQLAlchemy plus Postgres plus React plus Vite plus GitHub Actions; in countless 2025-and-2026 startups and internal tools, the SaaS dashboards and company ERP systems; in university capstones and bootcamp projects, because the auto-docs and component model make it such a friendly teaching stack; and, fittingly, in Alan's own `learning_v2604` and `fullstack_amazing_grace_v2`, both of which are layered FastAPI-plus-SQLAlchemy-plus-Postgres-plus-React apps — the latter using Vite and shared-cookie SSO exactly as we described it today. So this isn't a toy. It's the shape of how modern web software actually gets built — and now you can trace it, end to end, from one click to one row.
