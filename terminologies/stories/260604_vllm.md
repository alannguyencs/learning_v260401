# vLLM

Let me tell you where we're heading before we take a single step, because the punchline of today is almost a joke once you see it: the fastest way to serve a giant language model on a GPU turns out to be an idea your operating system has been using to manage RAM since the 1960s. That's it. That's vLLM. But to *feel* why that's clever, we have to build up the problem one layer at a time, and every layer is going to hand you the reason the next layer exists. So stay with the chain.

Start with the thing we're serving, the **large language model** itself — a Llama, a GPT-style transformer. The one fact about it that matters for us today is how it produces text: it generates **one token at a time**, and each new token is conditioned on every token that came before it. It doesn't write a sentence in one shot; it runs the same forward step over and over in a loop, emitting one piece, then feeding everything back in to emit the next.

```
LLM:  ... → token → token → token → ...   (one per step, each sees all prior)
```

And what *is* a token? It's the small unit of text the model reads and emits — usually a word piece. The word `"paging"` might be chopped into `pag` plus `ing`. Hold onto two things here. First, the token is the input/output unit, but attention never actually works on the token itself — it works on *vectors* derived from it, and we'll get to those in a moment. Second, and this is the one that'll bite us later: a sequence of length **N** is N tokens, and because generation is that loop emitting one per step, the longer the text gets, the more work each step has to do. Cost grows with N.

Now, *why* does cost grow with N? Because of **attention**, which is the heart of the transformer. At every step, the token being generated "looks back" at all the earlier tokens — it compares itself against every one of them to decide what to focus on next. For N tokens that's on the order of N×N comparisons, which is exactly why attention is the core source of cost. And notice the consequence that's going to drive everything: *each new token needs the representations of all the earlier tokens.* It can't proceed without them.

```
attention:  new token  ──looks back at──>  every earlier token   (N×N comparisons)
```

So what are these "representations" it looks back at? For each token, attention reads two float vectors — a **key** and a **value** — both derived from the token's embedding, not from the raw token. The key is what gets matched against the current query, via a dot product, to decide *how much* attention that token deserves. The value is the payload — once you've decided the weights, you sum the values according to those weights to decide *what* information actually flows forward. Key decides how much, value decides what.

```
key   →  matched (dot product)  →  how MUCH attention
value →  summed by those weights →  WHAT information passes on
```

Here's the first place a problem screams to be solved. Every step needs the keys and values of all previous tokens — so are we going to *recompute* every past token's key and value, from scratch, on every single step? That would be insane; the early tokens would be recomputed thousands of times. So instead the model computes each token's key and value once and **saves them**. That saved store is the **KV cache**. It grows by exactly one slot per token generated, and it lives on the GPU. Recompute becomes remember.

```
don't recompute past keys/values  →  save them once  →  KV cache (grows 1 slot / token)
```

Now, where exactly does that cache live, and why do we care? It lives in **GPU memory** — VRAM, the "40 GB" or "80 GB" you see advertised, what the hardware people call HBM. That same memory holds two things at once: the model's fixed weights, *and* every active request's growing KV cache. And here's the squeeze — VRAM is fast compared to ordinary CPU RAM, but it's *limited*, and when it fills up your only options are ugly: drop requests or shrink your batch. So VRAM is the scarce resource. The KV cache grows with every token and with every concurrent user, and it's fighting the model weights for that fixed, scarce space.

```
VRAM (HBM):  [ model weights ]  +  [ KV cache of every active request ]  ← fills up, scarce
```

But running out of room isn't even the worst of it. Here's the subtle killer. Suppose you give each request's KV cache one big *contiguous* slab of memory — one continuous block per sequence, which is the obvious thing to do. Now remember that requests start, stop, and grow at wildly different times. One finishes and frees its slab; another is mid-generation; a new one arrives needing space. Over time the free memory breaks into a patchwork of gaps, and even though the *total* free memory looks plenty, no single *contiguous* gap is big enough for the new request. This is **fragmentation**, and it's brutal — the older serving systems wasted sixty to eighty percent of their VRAM this way. You'd buy an 80 GB GPU and effectively use twenty.

```
contiguous slabs:  [req A][gap][req C][gap][gap]   ← total free looks big...
                   ...but no single gap fits a new request  =  fragmentation
```

And *this* is the exact moment the operating-system idea walks in, because operating systems solved this precise problem decades ago with **virtual memory and paging**. The OS lets a program believe it has one big continuous address space, but secretly it chops that space into fixed-size **pages** and scatters them across physical RAM **frames** wherever there's room, keeping a **page table** to remember which page sits where. Fixed-size chunks placed anywhere, with a lookup table to find them — that's the whole trick, and it's exactly what vLLM is about to borrow.

```
OS paging:  one "continuous" space  →  fixed-size pages  →  scattered RAM frames
                                       (page table remembers where each page went)
```

So vLLM takes that idea and points it straight at the KV cache. Instead of one contiguous slab per sequence, it splits each sequence's KV cache into fixed-size **blocks** — these are the pages — and stores each block wherever VRAM happens to have room, keeping a *block table*, which is just a page table, to find them again. The attention kernel can no longer assume the keys and values sit in one neat contiguous buffer, so it's rewritten to *walk the blocks* through that mapping, fetching keys and values block by block. That rewritten attention is **PagedAttention** — the name is literally "attention, but paged."

```
PagedAttention:  KV cache → fixed-size blocks → placed anywhere in VRAM
                 block table walks them during attention   (no contiguous slab needed)
```

And now the payoff falls right out. Because the blocks pack tightly together — blocks from many different sequences slotted into whatever space is free — the waste drops from sixty-to-eighty percent down to under about four percent. Tight packing means the GPU can hold *far* more concurrent requests at once, and that's the win: roughly two-to-four times higher throughput, and up to fourteen-to-twenty-four times versus plain vanilla Hugging Face Transformers, at similar latency — and the gains are biggest exactly where the cache is largest, on long sequences. The whole open-source serving engine built around PagedAttention, plus a scheduling trick called continuous batching, *is* **vLLM**. It doesn't make models; it *runs other people's models* for high-throughput, multi-user inference.

```
LLM → attention → KV cache → VRAM → fragmentation
   → paging → PagedAttention → vLLM (2–4× throughput, many more users)
```

Let me make that concrete, because it's almost embarrassingly simple to use. You `pip install vllm`, then `vllm serve meta-llama/Llama-3.1-8B-Instruct`, and you've got an OpenAI-compatible API on localhost — you point the ordinary OpenAI Python client at `http://localhost:8000/v1`, ask it to "explain paging in one sentence," and it answers. Now picture five hundred users hitting that one endpoint at the same time. Each user's growing KV cache is chopped into blocks scattered across VRAM; PagedAttention uses the block table to read those blocks during attention; and because there's almost no fragmentation, all five hundred sit on the GPU *together* instead of being turned away at the door. Every single term we built today is doing its job inside that one request flow.

```
500 users  →  500 KV caches  →  chopped into blocks across VRAM
           →  PagedAttention reads via block table  →  all 500 fit at once
```

Where will you actually run into this? The vLLM project lives on GitHub under the PyTorch Foundation and is everywhere; LMSYS used it for Chatbot Arena and FastChat to get up to thirty times more throughput on half the GPUs, serving tens of thousands of requests a day; Red Hat, NVIDIA, and the cloud providers ship it as a standard self-hosted inference backend; and any team self-hosting open-weights models like Llama, Mistral, or Qwen instead of paying for a hosted API is very likely running it.

And let me leave you with the confusions that trip people up, because each one is just a place to re-anchor what we learned. First, vLLM is *not a model* — it's the engine that *runs* models, and the "v" stands for *virtual*, as in virtual memory, not "version." Second, don't confuse **PagedAttention with FlashAttention**: FlashAttention speeds up the attention *computation*, PagedAttention optimizes how the KV cache is *stored* — different problems, and people happily use both together. Third, the **KV cache and the model weights** both live in VRAM, but the weights are fixed and shared across all requests while the cache is per-request and grows as text is generated — keep those separate in your head. And finally, vLLM versus Ollama or TGI or TensorRT-LLM: they all serve LLMs, but vLLM is aimed at high-throughput multi-user serving, Ollama at easy single-user local use, and the others are competing engines in the same arena. Keep the chain — LLM, attention, KV cache, VRAM, fragmentation, paging, PagedAttention, vLLM — and the whole system is just one problem politely forcing the next solution into existence.
